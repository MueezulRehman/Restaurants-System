1. Executive Summary TasteHut is a cloud -based, multi -tenant SaaS platform that allows a single Super Admin to onboard and manage multiple independent businesses — restaurants, retail stores, cafes, or any point -of-sale business. Each business gets its own fully isolated envir onment: its own staff, inventory, POS, sales records, expenses, invoices, feedback, and customer -facing storefront. The system supports three primary roles: • Super Admin — owns and operates the SaaS platform. Onboards businesses, sets their type, controls which modules they can access, manages subscription plans, and reviews all feedback. • Business Manager — manages a single business. Has access only to the modules granted by Super Admin: menu/inventory, POS, orders, sales, expenses, staff, attendance, salary, reports, and customer feedback. • Customer — browses a restaurant's public storefront, adds items to cart, places orders, tracks delivery, and submits feedback to the manager. 2. Business Types Supported When the Super Admin registers a new business, they select the business type. The type determines which modules and sidebar items the Manager sees, making the same codebase serve multiple verticals. Business Type Modules Enabled Customer Storefront Restaurant POS, Menu, Categories, Variants, Deals, Orders, Cashbook, Expenses, Staff, HR, Reports, Feedback Yes — full menu + ordering Retail / Shop POS, Inventory, Categories, Variants, Cashbook, Expenses, Staff, HR, Reports, Feedback No (admin POS only) Cafe / Bakery POS, Menu, Categories, Variants, Deals, Orders, Cashbook, Expenses, Staff, HR, Reports, Feedback Optional General Business POS, Inventory, Variants, Cashbook, Expenses, Staff, HR, Reports, Feedback No ⚠ Note: Future business types can be added without changing the core codebase — only the enabled_modules JSON column on the restaurants table needs to be updated. 3. Role Separation 3.1 Super Admin Super Admin is the platform owner. After login they land on the Businesses dashboard. Their sidebar contains only platform -level tools: • Businesses — add, edit, activate, deactivate, assign plan • Business Type selector — pick type and enable/disable modules per business • Subscription & Plans — view active subscriptions, overdue payments, trial expirations • Feedback Centre — read all manager suggestions and customer complaints across all businesses ⚠ Note: Super Admin has ZERO access to any business's data (menu, orders, cashbook, staff). Visiting /admin/dashboard or /admin/orders as super admin returns HTTP 403.

It must support fast, keyboard and scanner -driven operation with no mouse clicks required for a standard sale. 5.1 Item Lookup — Four Methods • Barcode Scanner — plug in any USB HID scanner; the POS page listens to rapid keystrokes followed by Enter and auto -adds the item to cart • Item Number / SKU — type the SKU and press Enter • Item Name Search — type partial name; a live -search dropdown shows matches instantly • Category Browse — click a category tab to see the item grid, then click to add 5.1.1 Barcode Entry Workflow — Adding an Item (Implementation Spec) There are exactly two ways a manager gets a barcode into an item's record. Both write to the same field, so either one is sufficient — the build must support both.

 • Way 1 — Type it manually. On Menu Items → Add New Item, the form has a plain text "Barcode" field. The manager types or pastes the barcode number in (e.g. 6901443391356) and saves. No special formatting or validation beyond uniqueness -per-business is required. • Way 2 — Scan directly into the form (easiest). The manager plugs in a USB barcode scanner, clicks inside the Barcode field on the Add Item form, then points the scanner at the product. The scanner fires the number into the field automatically — functionally identical to typing it, just instant and erro r-free. No click - to-add step or special handler is needed; the field just needs focus. Full item setup flow (step by step): • 1. Manager opens Add New Item • 2. Clicks the Barcode field → scans the product → number fills in automatically (or types/pastes it manually) • 3. Fills in the rest: name, category, price, cost price, stock quantity • 4. If the item has variants (colour, size, etc.) → enables the Variants toggle and adds them • 5. Uploads a photo (optional) • 6. Saves Then, at the POS, when that same product is scanned at the counter, the system looks up the barcode in the database and adds it to the cart instantly — this is the exact mechanism described in 5.1's "Barcode Scanner" method. ⚠ Note: A barcode scanner is just a keyboard in disguise — it types the number and presses Enter. No special software or driver is needed; any cheap USB HID scanner works out of the box. This means the "Barcode" input on both the Add Item form and the POS search b ox are ordinary text inputs — no scanner -specific SDK, browser permission, or hardware integration is required for USB scanning. (This is separate from optional camera -based scanning, which is an added convenience, not a requirement.) 5.2 Product Variants When an item has variants (e.g. iPhone 16 with options for colour, storage size, or battery health), the manager selects the variant before the item is added to cart. Variants are configured per item in the Menu/Inventory section. Variant examples: • Colour — Black, White, Desert Titanium, Natural Titanium • Storage Size — 128GB, 256GB, 512GB, 1TB • Battery Health — 100%, 95 –99%, 90 –94% • Size — S, M, L, XL (clothing) • Each variant combination can have its own price and stock quantity ⚠ Note: When a variant item is added to cart, the cart line shows: Item Name + Variant (e.g. "iPhone 16 — Black / 256GB"), Qty, Unit Price, Line Total. 5.3 Cart & Billing • Each cart line shows: item name, selected variant, qty (editable inline), unit price, line total • Manager can adjust quantity, apply item -level or cart -level discount, or remove a line • Cart summary: subtotal, discount, tax (configurable per business), grand total • Payment modes: Cash, Card, Split (future) • On "Complete Sale": order saved to DB, stock decremented per variant, invoice auto -generated

Order Privacy & Handling 7.1 Customer Order Privacy Each order is assigned a unique, cryptographically random tracking token at creation time. Customers can only access an order via its token URL (e.g. /track/a3f9c2b1). There is no order listing page for customers — they cannot browse or search other orders . • Token is generated with Laravel's Str::uuid() or random_bytes(16) — not guessable • Customer tracking page shows only: order status, items ordered, total — no other customer's name, phone, or address is ever visible • No authentication required for tracking — just the token URL • If someone tries to guess a token and it doesn't exist, they receive a 404 — not a "wrong token" message

Multi -Tenancy & Data Isolation Every tenant model carries a restaurant_id and uses a global Eloquent scope (BelongsToRestaurant trait) that automatically filters every query to the logged -in user's restaurant_id. Key guarantees: • A manager from Business A cannot read, edit, or delete Business B's data — even by guessing a record ID in the URL (the row won't be found; Laravel returns 404) • New records automatically inherit the creator's restaurant_id • Super Admin is exempt from this scope for platform -level queries • Customer orders are isolated by tracking token — no enumeration possible

13.1 Future -Proofing: Custom DB Structure Per Business Some enterprise clients may eventually require a completely separate database or schema (e.g. a large retail chain that wants their data on their own server). The current architecture already supports this via the following approach: • Step 1 — Add a db_connection column to the restaurants table (default: null = shared DB) • Step 2 — Store the custom DB credentials (host, database, username, password) encrypted in that column • Step 3 — In the BelongsToRestaurant trait's bootBelongsToRestaurant() method, before applying the scope, switch the DB connection: DB::purge() → Config::set('database.connections.tenant', ...) → DB::reconnect('tenant') • Step 4 — The rest of the application works identically — no controller or model changes needed 13.2 Migrating an Existing Business to a New System If a business needs to move their historical data to a new or upgraded system, the safe migration process is: • 1. Export all records for that restaurant_id using php artisan db:export --restaurant=X (custom artisan command to be built) • 2. The export produces a JSON or SQL dump scoped to that business only — no other business data included • 3. Import into the new system/database using the matching import command • 4. Validate record counts and spot -check key records (orders, invoices, cashbook) • 5. Update the db_connection column if the business is moving to their own database ⚠ Note: No data is ever deleted during migration. The original records stay in the shared DB until the business explicitly requests deletion (right to erasure). 14. Roles, Permissions & Access Control (Current Implementation) Access control today is enforced by a combination of three mechanisms — not by named route gates (e.g. a 'can:super -admin -only' policy). Documenting the real mechanism matters because it changes where a future developer should look when debugging an access issue. 16.1 The Three Enforcement Layers Layer 1 — Auth guards — two separate Laravel auth guards Column Type & Notes web guard staff accounts (super_admin, admin/manager, cashier, kitchen, rider) — the users table customer guard customer accounts — the customers table, entirely separate session/login Layer 2 — Controller -level role checks — PHP checks inside controllers, not route middleware Column Type & Notes User::isSuperAdmin() true only for role === 'super_admin' User::isRestaurantManager() true for role in ['admin', 'manager'] abort_unless(...) used in e.g. ManagerDashboardController to 403 anyone who isn't staff for that restaurant Layer 3 — BelongsToRestaurant trait — a global Eloquent scope on every tenant -owned model Column Type & Notes Auto -filter queries automatically add WHERE restaurant_id = X for the current user's restaurant Auto -fill new records automatically get restaurant_id set on create Super admin exception unscoped (sees everything) unless currently impersonating a restaurant via the Tenancy helper Applies to Category, MenuItem, Deal, Order, Cashbook, Expense, Attendance, Salary, Product, Sale ⚠ Recommendation: route -level role middleware (e.g. a simple EnsureRole::class middleware checking the role before the controller even runs) would add a defense -in-depth layer on top of Layer 2's controller checks. Today, a mistake in a single controller's abort_unless() ca ll is the only thing standing between a logged -in user and a route meant for a different role. Not urgent while the team is one developer, but worth adding before onboarding other developers. 16.2 Permissions Matrix Capability Super Admin Restaurant Admin/Manager Customer Create/edit/suspend any restaurant Yes No No
